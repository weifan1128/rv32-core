# 07 — AXI4 協定與本專案整合

## 一、AXI4 是什麼？

AXI4（Advanced eXtensible Interface 4）是 ARM AMBA 匯流排協定，專為高效能 SoC 設計。
本專案使用 AXI4 連接 CPU（Master）與 SRAM（Slave），取代原本 CPU 直接接 SRAM 的方式。

---

## 二、五條獨立通道

AXI4 把傳輸拆成五條**獨立**的通道，各有自己的 VALID/READY 握手：

| 通道 | 縮寫 | 方向（Master → Slave） | 用途 |
|------|------|----------------------|------|
| Write Address | AW | M → S | 寫入目標地址 |
| Write Data    | W  | M → S | 寫入資料 |
| Write Response| B  | S → M | 寫入完成回應 |
| Read Address  | AR | M → S | 讀取目標地址 |
| Read Data     | R  | S → M | 讀取資料 |

> **讀**只用 AR + R；**寫**只用 AW + W + B

---

## 三、握手規則（Handshake）

每條通道都用 **VALID / READY** 握手：

```
          VALID ──────────────┐
          READY ──────┐       │
                      ↓       ↓
clk  ─────────────────┬───────┬───
                      │ transfer │
```

- **傳輸發生**：VALID 與 READY 在同一個時脈上升緣同時為 high
- **VALID 一旦拉高，不可在握手前拉低**（AXI spec 規定）
- READY 可以比 VALID 早、晚，或同時拉高，都合法

---

## 四、本專案拓撲

```
CPU (IF stage)  ── M0 (read only) ──┐
                                     ├── AXI Interconnect ── S0 (IM, 0x0000–0x7FFF)
CPU (MEM stage) ── M1 (read+write) ─┤
                                     └─────────────────────── S1 (DM, 0x8000–0xFFFF)
```

| Master | 可用通道 | 對應 CPU 操作 |
|--------|---------|--------------|
| M0 | AR, R | IF 取指（只讀 IM） |
| M1 | AW, W, B, AR, R | MEM 讀寫（讀/寫 DM） |

**Interconnect 路由規則（依地址）：**
- `addr[15] == 0`（0x0000–0x7FFF）→ S0（IM）
- `addr[15] == 1`（0x8000–0xFFFF）→ S1（DM）

---

## 五、關鍵參數（`AXI_define.svh`）

| 參數 | 值 | 說明 |
|------|----|------|
| `AXI_ID_BITS` | 4 | Master 端 transaction ID 寬度 |
| `AXI_IDS_BITS` | 8 | Slave 端 ID 寬度（4-bit master ID + 4-bit routing tag，供 interconnect demux） |
| `AXI_ADDR_BITS` | 32 | 地址寬度 |
| `AXI_DATA_BITS` | 32 | 資料寬度（32-bit word） |
| `AXI_LEN_BITS` | 4 | Burst length 欄位寬度 |
| `AXI_LEN_ONE` | `4'h0` | 單筆 burst（LEN=0 代表 1 beat） |
| `AXI_BURST_INC` | `2'h1` | INCR burst（地址遞增型） |
| `AXI_RESP_OKAY` | `2'h0` | 正常回應 |

---

## 六、Burst 說明

AXI4 支援 burst 傳輸（一次 AR/AW → 多個 data beat）。本專案所有傳輸均為 **單筆（LEN=0, 1 beat）**：

```
ARLEN = 4'h0  → 1 beat（LEN 值 = 實際 beat 數 - 1）
ARBURST = 2'h1 → INCR（標準遞增型）
```

---

## 七、v1.1 — In-Order（本次實作）

- CPU 每次**只發出一筆**請求，等收到回應才繼續
- 沒有同時多筆 in-flight transaction → 不需要 ID 追蹤
- 實作重點：
  - **IF stall**：AR 發出後，等 `RVALID & RREADY` 才放行 PC 推進
  - **MEM stall**：
    - Load：AR → 等 R 回來才 WB
    - Store：AW + W 同時發，等 B 回來才繼續

### 寫入時序（v1.1）

```
cycle:    1        2        3
AW:   VALID=1  READY=1  ——
W:    VALID=1  READY=1  ——
B:    ——       VALID=1  READY=1  ← CPU stall until this
```

### 讀取時序（v1.1）

```
cycle:    1        2        3
AR:   VALID=1  READY=1  ——
R:    ——       VALID=1  READY=1  ← CPU stall until this
```

---

## 八、v1.2 — Outstanding（待實作）

- CPU 可同時有**多筆 in-flight** 請求（不等前一筆回應就發下一筆）
- Slave 可能亂序回應 → 需靠 **ID** 對應回哪個請求
- Interconnect 需要：
  - 記錄各 ID 對應的 master
  - 收到 `BID` / `RID` 後，根據 `AXI_IDS_BITS`（8-bit）中的 routing tag 把回應送回正確 master
- CPU 端需要 **re-order buffer** 或保證只對不同地址發 outstanding 請求

---

## 九、常見坑

| 問題 | 說明 |
|------|------|
| AW 和 W 沒同步 | AXI spec 允許 AW 先於 W，但 Slave 若不支援會 deadlock |
| VALID 拉高後提早拉低 | 違反 AXI spec，會導致 Slave 遺漏握手 |
| 忘記等 B channel | Store 操作必須等 BVALID，否則後續讀可能看到舊值 |
| ID 寬度混用 | Master 端用 `AXI_ID_BITS`（4），Slave 端用 `AXI_IDS_BITS`（8），interconnect 負責拼接 |
